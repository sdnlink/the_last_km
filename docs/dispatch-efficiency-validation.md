# 调度频率与定向返工验证

本轮使用 ScriptedProvider 启动真实子进程，通过 Supervisor 的实际需求完善、实现、审核、AUD、验收和恢复逻辑进行确定性测试。没有调用付费模型；验证的是调度与门禁，不代表真实模型每次都会给出正确代码。

## 问题与修复

此前 review-first 在源码指纹变化时立即审核，绕过 `review_every`，导致未完成的正常实现进展也逐轮调用 reviewer。移除该额外触发条件后，默认连续 5 轮 worker 工作才进行进度审核；完成候选、外部阻塞及质量策略指定的规模/超时检查点仍及时审核。`0` 关闭周期审核，`1` 显式逐轮审核。

兼容下一轮需求功能时，还发现需求完善结果未保存 cycle，恢复可能重复完善已有 ready 需求。现在保存轮次标识，下一轮从新的需求交接开始，保留既有已提交成果，不把上一轮结论当成本轮缺陷。启动 worker 或需求 reviewer 前若已收到停止，则不再调用模型。

## 调度断言

下表调用数包含初始需求完善；进度与阻塞场景中的 max_rounds 表示测试预算结束，不表示任务已完成。

| 场景 | worker 调用 | reviewer 调用 | 验证重点 |
| --- | ---: | ---: | --- |
| 首次实现即通过 | 1 | 2 | 一次需求完善、一次独立交付审核 |
| 连续三轮修改，默认间隔 | 3 | 1 | 仅完善需求，未到周期不重复审核 |
| 三轮修改，间隔设为 3 | 3 | 2 | 第三轮触发一次进度审核 |
| 关闭周期审核，第二轮完成 | 2 | 2 | 完成候选仍立即审核 |
| 关闭周期审核，出现外部阻塞 | 1 | 2 | 阻塞仍交给 reviewer 核查 |
| 一个局部缺陷，修复后通过 | 2 | 3 | 反馈携带 AUD-1、文件、触发条件及最小修复建议，保留 verified.py，审核关闭准确 AUD |
| 审核结论格式错误后修复 | 1 | 3 | 只重试 reviewer，不重新实现；调用仍计预算 |
| 失败审核恢复，候选未变化 | 恢复阶段 0 | 恢复阶段 1 | 只续审，不调用 worker；源码或人工要求变化则失效 |
| worker 启动前停止 | 0 | 1 | 已完成需求完善，但不再启动实现 |

测试同时覆盖：认证错误直接停止；reviewer 写入项目拒绝交付；未受影响模块和已关闭 AUD 的范围复用；共享依赖或证据变化重新验证；Git tree 增量审核基线恢复；固定检查失败不提交；业务发布、索引恢复和用户暂存保护。减少调度没有放宽这些门禁。

## 复跑

```bash
.venv/bin/python -m unittest tests.test_review_efficiency tests.test_requirement_follow_up tests.test_review_first -q
.venv/bin/python -m unittest discover -s tests -q
node --test tests/test_console_requests.mjs tests/test_review_only_boundary.mjs
git diff --check
```

局部修复的提示词要求 reviewer 一次提交当前已知阻塞，给出 AUD、验收条款、文件或符号、触发输入、预期与实际、最小修改范围及验证命令。worker 只修复相关缺口，保留已验证行为；reviewer 复查差异、相关依赖及未关闭问题。watcher 最终仍独立执行固定检查，不以历史通过替代本次验收。模型遵循修复范围的程度仍需真实任务观测，不能由提示词或调度测试保证。

## 后续边界检查

提交上述调度优化后，又复现并修复三项需求交接问题：

- 否定指令包含继续开发关键词时误触发：中文“不要/禁止/不需要”和英文 “Do not / Don't / never” 的相关指令不再授权新需求；集成测试确认只进行本次交付的 1 次 worker 和 2 次 reviewer 调用。
- 恢复需求完善时使用默认第 0 轮日志，覆盖最初的需求结论：后续审核编号由已保存的需求轮次计算；测试逐字节核对首次需求文件没有被改写，并检查独立后续轮次记录。
- 写入超过 32 轮后，检查点无法通过恢复校验：运行阶段在相同上限停止，保存已提交成果，不调用下一轮 reviewer；恢复也保持停止，不继续增加模型调用。

需求交接和调度专项 33 项通过。新增用例位于 `tests/test_requirement_follow_up.py`，包含否定语句、否定任务交付、恢复日志保护及轮次上限后恢复；上限测试使用缩小的常量验证同一生产路径，不实际调用 32 轮模型。

本轮最终全量验证：Python 569 项通过（84.103 秒），两份 Node 前端测试通过，`git diff --check` 通过。未调用付费模型，未变更历史任务状态。

## worker 时间调度优化

真实 Grok 4.7 自检任务暴露出：单轮配置 900 秒，却因质量策略 `review_interval_s=600` 在 600 秒被终止，停止前仍在编辑和验证。review-first 现将审核间隔改为 worker 累计工作时长达到阈值后，在正常返回处审核；正常审核不主动丢弃 worker 会话。累计值随 `review_schedule.worker_seconds_since_review` 保存，只有有效业务审核后重置。单轮硬超时、输出空闲超时、总预算和既有 legacy 时间检查点语义保留。

worker 会收到一次只处理一个 reviewer 条目或局部修复的交接要求，以及单轮、空闲和剩余总预算提示。新增 `tests/test_worker_time_management.py` 覆盖审核间隔不缩短硬上限、跨轮累积时间与会话续接、恢复计数和硬超时仍生效。与质量策略、效率相关测试合计 49 项通过，两份 Node 测试通过。

维护恢复沿原任务和既有 reviewer 结论继续，不创建新开发任务、不重置调用预算。运行参数扣除维护暂停时间，保持最初一小时截止；当前 Grok 候选仍需独立审核，维护验证不等于获批提交。
