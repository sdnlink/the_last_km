# 提交与归档可靠性检查

本次检查直接针对本地 Git 事务、候选断点和历史清理，未调用付费模型，也未更改旧任务的真实验收状态。以下缺陷均先在临时 Git 仓库复现，再验证修复。

| 缺陷 | 触发方式与原行为 | 修复及门禁 |
| --- | --- | --- |
| 跨轮删除漏提交 | 第一轮新增文件并提交，第二轮删除该文件；文件既不在初始快照，也不在当前候选中，旧构建逻辑漏掉删除，导致 HEAD 保留已删除代码 | 业务 tree 同时考虑初始、当前及最近已发布候选的路径；删除、文件/目录互换均须与当前候选一致，保留其他目录及无关暂存 |
| 损坏归档误通过 | 归档恢复后破坏 bundle 的 pack 数据但保留头部，再次清理；只核对 list-heads 无法发现损坏，会删除仍有效的审计引用 | 新归档、已有归档复用及恢复均在隔离的临时裸仓库实际解包验证对象数据；验证失败保留原引用，不以头部或文件存在代替可恢复性 |
| 候选引用与检查点中断不一致 | 临时工作引用已更新，git-history.json 尚未保存时中断；下一次误报引用被外部修改。首次初始化也有同样窗口 | work-checkpoint.json 先持久化前后状态，再更新引用和检查点；恢复须核对任务身份、业务 HEAD、引用前后值、提交父链及候选 tree。外部篡改仍拒绝自动覆盖 |
| 索引半写无法恢复 | 业务与审计引用已提交，写 index.lock 时只写入一部分便中断；原逻辑只接受完整旧值/新值，恢复因此卡住 | 只有锁文件 inode 属于本次发布、引用匹配已提交事务、原索引未被外部修改，且残留字节是已验证目标索引前缀时，才允许补全。用户无关暂存保持原内容 |
| 任务启动前的删除漏提交 | 启动任务前已删除受 Git 跟踪的文件；该文件不在任务初始快照或候选中，审核通过后业务提交仍保留文件 | 构造业务 tree 时同时检查业务 HEAD 中属于当前项目源码范围的路径；候选不存在的源码按删除提交，其他项目目录、运行数据和排除的构建产物仍保留 |
| 失败任务残留候选引用 | 新任务没有任何批准记录就达到轮数上限；显式清理失败任务时因审计 head 为空直接返回，运行目录删除后仍留下候选引用 | 仅在明确纳入清理的结束任务上，核对候选引用归属和旧值，保存无批准历史的清理记录，再删除候选引用；中断可重试，外部修改则停止。不生成候选代码备份，不修改工作区或业务 HEAD |

候选恢复记录只保留最新一份事务，成功后删除；不创建工作区备份。运行目录清理、审计迁移/归档/恢复，以及 Web 删除、角色修改共用的非运行检查，都会保留尚待恢复的发布记录或候选检查点。锁文件或待恢复数据不因心跳过期被清理。

新增测试位于 `tests/test_business_publication.py` 和 `tests/test_git_maintenance.py`，覆盖删除提交、文件/目录转换、损坏归档、首次/逐轮候选保存中断、半写索引、外部改动拒绝及恢复中数据保留。既有业务批准门禁、暂存冲突和归档过期测试继续执行。

后续回归还覆盖任务启动前的删除、子目录和排除路径保留、未批准失败候选的默认保留、显式清理、中断续清、外部引用变更保护，以及运行目录清理时移除候选引用。没有批准记录的任务无法恢复出已批准审计；清理记录明确标记 `no_approved_history`。

最新验证结果：`.venv/bin/python -m unittest discover -s tests -q` 共 551 项通过（82.616 秒）；两份 Node 前端测试通过，`git diff --check` 通过。真实 Web 控制台只读检查正常，两项历史任务保持 `budget_exceeded` / `stopped`，没有据此标记为完成。本轮未调用付费模型。
