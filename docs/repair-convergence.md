# 有限修复与检查复用

真实自我迭代任务反复经历“完成候选、全量回归、审核发现新边界、继续返工”。第 9 轮最终交付了恢复模块，但第 10 轮在源码没有变化时又为需求级报告执行了一遍同样的全量检查。期间缺口反复分批出现，已有模块的缓存批准还可能被当成未完成审核重放，随后因为没有新模块可接受而被拒绝。

本次修改针对可确定的调度浪费，没有缩减原需求、删除固定检查或自动关闭审计项。

## 修复先预检

普通 review-first 代码任务在同一交付范围已有至少两次有效的缺口审核后，且仍有待处理 AUD，下一份完成候选先进行只读预检。审查器检查当前修复的入口、调用方、清理与异常路径，一次汇总已知阻塞。

拒绝审核可以不填写 `module_ids`。此时从该审核对应的 Worker 候选恢复范围，而非将其当成无范围或全项目问题。同一候选的多次报告纠错只计为一次返工，不能凑出预检触发次数。

预检发现明确缺口时，按原 AUD 流程反馈 worker，该候选不先运行昂贵的固定检查。预检就绪时，继续正常的 Watcher 检查与新的独立正式审核。预检不应用审计关闭提案，不产生接受记录或业务提交；测试失败仍禁止交付。预检原文保存为 `NNN-reviewer-preflight.log`、`NNN-reviewer-preflight-text.md`、`NNN-reviewer-preflight-prompt.md`，页面可读取，并随对应轮次清理。工作流事件明确说明预检不等于正式验收。

预检沿用原调用、时间、只读隔离和控制边界。停止或认证错误不绕过；审核改写工作区时保留现场并拒绝接受。预检计入模型预算，可能增加一次审查调用，收益来自更早拒绝明显不完整的修复；不承诺模型能一次找全全部缺陷。逐函数任务、Paseo 审核以及非代码任务保持原检查／审核协议。

## 完成模块后直接推进

已接受模块的交付记录不再被识别为尚未完成的审核。执行器继续下一个模块或做需求级核验，已接受代码保留，不产生同一模块的重复拒绝记录。

已接受模块转交后续模块、或所有模块已接受后转交需求级候选时，源码不变可复用最后一次模块交付的完整检查结果。复用同时要求命令、检查超时、角色与模型、原需求、验收条件、质量策略、人工指令、需求轮次及业务输入版本一致。原模块必须有实际有效的独立批准，日志须仍匹配原哈希。后续模块增加检查命令时重新执行；只有测试通过而没有模块批准也不能复用。任一条件不符则正常重跑，不从更早的成功结果跳过最近失败结果。

复用只涉及检查，不复用后续模块及最终审核。当前轮次回执绑定新的报告范围并记录来源，日志原字节复制到当前轮，旧轮清理不会使最终证据失效。需求级覆盖、审计关闭、停止、预算和发布检查全部保留。需要更新部署或外部状态的非代码任务不使用此跨轮路径。

## 验证

`tests/test_repair_convergence.py` 使用临时项目、真实子进程和脚本化模型覆盖完整调度：四份候选中的第三份在预检被拒绝，不执行该轮固定检查；第四份预检就绪后，先执行固定检查，再获得正式审核。另一个模块到需求级交付场景保持两次 worker 和三次 reviewer 调用，仅执行一次固定检查；实际 Git 提交与停止后恢复也保留该性质，最终审核仍新调用。

反例覆盖预检后检查失败、只读审核写入、检查日志篡改、源码改变、指令改变、命令改变、模型改变、需求轮次和业务输入版本改变。预检拒绝历史跨恢复保留，工作流事件可读，预检日志随轮次清理。

首次实现的验证：新增 9 项行为回归通过；完整 Python 回归 1203 项通过（339.136 秒）；`node --test tests/*.mjs` 的 14 个测试文件全部通过；离线 `auto_moniter selftest` 通过，付费模型调用为 0。`git diff --check` 通过。

建议后续任务继续使用现有逐函数派单，按依赖拆成可验收的实现与验证项。模块影响范围应来自真实依赖与审核证据；范围不明时继续保守重验，不从文字猜测未经批准的窄范围。修复提示现在要求一次完成当前模块的相关调用链，再交付该模块，避免把所有待办模块一起扩展。
