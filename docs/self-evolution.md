# 系统自身代码的自动进化

`auto-moniter evolve` 会修改 auto-moniter 自身源码。它与仅保存经验的 `experience` 不同：由旧版本控制器监督模型生成新版本，并在独立审核、完整回归和启用检查通过后更新本地源分支。

```sh
auto-moniter evolve --cwd /path/to/auto_moniter --provider codex --reviewer claude
```

默认最多执行 3 个周期，共享 1 小时和 20 次模型调用预算。周期之间不会重置额度；当前候选失败会留在隔离工作副本中，系统选择其他未处理问题。停止、预算耗尽、原分支有并发修改、基线不可验证或启用失败回退时结束当前循环，保留原因和证据。

## 一个周期怎样推进

1. 从已停止任务中汇总监督程序异常、检查点恢复异常和非法计划等运行证据。普通业务测试失败不是修改监督器的理由。若没有新的历史问题，则由 Reviewer 主动检查自身源码，寻找一个可复现的正确性、恢复或验收缺陷；无法建立缺陷时不做凑数修改。
2. 要求源仓库位于业务分支且工作区干净。创建外部工作副本及独立 `evolution/...` 分支，先跑旧版本全量基线。源分支有任务持锁或本地改动时保留现场，不重置、不清理。
3. 复用 Worker、Reviewer、Watcher 完整链路：需求审查、完整有限计划、实施、行为回归、独立审核及候选分支上的本地发布。必须有真实运行时代码变化和新增回归测试；不能削弱既有测试、CI 和验收配置。
4. 原控制器从候选提交再创建一份干净的验证副本，独立执行编译、全部 Python 回归、离线自检、提交差异格式检查及全部 Node 测试，避免借用实施副本里的忽略文件、缓存或临时依赖。检查项由控制器确定，候选不能通过改一份“通过报告”替代执行。
5. 确认报告已最终完成、对应精确候选提交、工作副本没有未提交变化、检查没有改写源码。原分支仍与启动基线相同且干净时，以 fast-forward 更新本地源分支；不强推、不重写历史。
6. 该项目的控制台正在运行时，用现有重启流程载入新版本并等待 HTTP 就绪，保留已启动任务。控制台未运行时，更新对下次启动生效。现有独立监督进程继续使用其已载入版本，不在执行中替换函数。
7. 新版本启用失败时，创建恢复旧源码树的新提交并 fast-forward，再尝试启用旧控制台。用户或其他任务产生了改动时保留现场，禁止强制回滚。成功、失败、检查日志、候选和旧提交均保存在演进记录中。

独立副本不会复制实施环境的私有依赖。控制器为验证子进程提供受控的 Python/Python3 启动包装，并在副本的 `.venv/bin` 提供同样入口，使固定 PATH 的启动脚本也使用当前受支持的解释器和既有依赖；不创建另一个需要下载依赖的虚拟环境。包装内容改变会使验证失败，进程外 PATH 不变。

## 查看及恢复

只读查看下一改进计划，不调用模型或创建状态目录：

```sh
auto-moniter evolve --cwd /path/to/auto_moniter --plan-only
```

可重复提供 `--evidence-root <运行目录的父目录>`。`--cycles`、`--max-runtime`、`--max-agent-calls` 控制整个循环。演进记录位于私有项目状态目录的 `evolution/<周期>/evolution.json`，每周期保留独立工作副本、监督运行及基线/候选检查日志。

发布阶段中断，可对原周期重新核对并恢复，不重新实现或重复提交：

```sh
auto-moniter evolve --cwd /path/to/auto_moniter --recover /private/state/evolution/<周期>
```

恢复会核对候选、独立验收和所有检查日志哈希；证据改变时拒绝更新。已完成的 fast-forward 只补记结果。基线相同、证据相同且已失败的改进不被盲目重复派发；主动审查也按源码版本去重。

它不会推送远程或无限扩大预算。升级期间机器断电等情况可能保留工作副本和恢复记录；`--recover` 当前覆盖已经通过验证的发布/启用阶段，未完成的实施仍保留正常 Supervisor 检查点。模型凭据、原生测试工具或外部服务不可用会形成明确限制，不通过删测试、虚报成功或切换为无审核模式继续。
