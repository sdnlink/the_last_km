## 低效原因

1. Grok 1.0.77 的真实流式协议未被正确解析，且 `--json-schema` 对照探针只返回结论、不调用工具。前几轮没有实际推进实现；这属于执行器兼容问题。已修复协议解析和工具调用方式。
2. 中文输入请求检测把“请求测试。……授权记录”跨句误认成等待人工，提前杀掉正常 reviewer。另有操作员计划重载中断。这些中断原先也重新进入 worker，而非续审已完成候选。
3. 第 8 轮原始业务审核通过，但关闭提案给出 7/5 条证据，超过运行时 1～4 条约束。旧 schema 未说明条数且反馈笼统，导致 worker 重跑测试、再次提交后才能发现是 reviewer 格式问题。
4. 每轮要求同时执行两个等价 unittest discover，再把结果复制到源码文档。文档/日志变化又改变全局指纹，引发新一轮复核。第 8、9 轮等有大量重复取证，并非相应数量的新能力。
5. 任意源码变化会重新打开全部已关闭 AUD；模块虽支持影响范围，但只有每个模块都配置 `files` 才启用。旧结论无法有效保留。
6. reviewer 每次都被强制要求同时核对当轮和整份累计 diff，且提示里又重复附带 HEAD 全量 diff，增加重复阅读。新增反馈中有些只给“补齐测试”，没有一次列出所有命令入口，第二模块到后续轮次才发现 `modules[].checks` 绕过。
7. watcher 用登录 shell `sh -lc`，PATH 与 worker 不同，找不到现有 Codex，7 个夹具因此返回 invalid。worker 又误用嵌套 TMPDIR 假设修旧测试，触发基线保护停止。原测试已恢复；主机同款环境下 483 项复核通过，确认 PATH 是该次失败的已证实原因。
8. 运行中新增角色切换、Grok 适配和监督器修补等范围，并多次重载，也消耗了原预算。这一部分属于操作过程中的范围扩张，不能都归因于模型速度。

其中有效返工包括：恢复失败回滚、continue/blocked 错误反馈丢失、模块命令绕过、真实表单请求接线、失实文档修正。应保留这些门禁，减少没有新输入的重复实现和取证。

## 本次落实的改进

- reviewer 格式、暂时执行失败及遗漏候选哈希，在同一候选上有界修复一次。失败尝试单独记录，不生成新的 worker 轮次，也不关闭任何 AUD 或提交。认证失败直接停止，所有重试仍计入预算。
- 持久保存未完成的审核阶段。恢复时只有源码、worker 完成结论、用户补充要求均匹配才复用候选；变更输入后重新走 worker。已有 worker 轮次上限不会阻止对最后一份有效候选续审，但不允许超出 agent/时间预算。
- 保存上一次有效业务审核 tree，默认检查其后差异及影响链；保留累计差异给集成复核使用。首次审核、共享改动和最终验收不能省略。
- 模块与 AUD 共用影响范围。缺少范围的模块保守受影响，其余已声明范围的独立模块不必全部回退；依赖、证据文件、共享未知文件变化仍触发重验。范围只能由用户提供，不能让 AI 自行缩小。
- reviewer 必须给可定位、可复现、可验证的修复建议，区分推断和实测；一次列出已知阻塞项。worker 避免等价全量检查重复运行，watcher 保留独立验收职责。
- watcher 使用继承 PATH 的非登录 shell，减少执行环境漂移。

新增 `tests/test_review_efficiency.py` 通过真实子进程和监督循环覆盖：只重试 reviewer、恢复续审、变更输入失效、预算和认证边界、只读写入拒绝、PATH 继承、模块/AUD 影响传播及审核差异基线恢复。原有关闭门禁测试也继续验证：非法提案不得关闭问题或产生批准提交，合法提案才能推进。

## 结论复用的边界

同一代码版本、相同要求、未变化的证据，不需要 worker 重新实现，也不应因轮次变化重跑两种等价全量检查。明确的业务反例、受影响依赖、失败检查、被保护验收资产改变或新要求到达，必须重新验证对应范围。最终交付仍要通过当前候选的独立审核、全部开放 AUD 关闭和 watcher 固定检查。

本次修复经过自动测试，并非重新完成了旧任务的真实 Grok/Codex 两小时验收。原任务的 budget_exceeded、未完成 FINAL 等历史结果保留。
